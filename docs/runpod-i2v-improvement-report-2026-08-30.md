# RunPod i2v 성능·품질 진단 보고

- 작성일: 2026-08-30
- 대상: DOBEDUB Studio v4 / RunPod Serverless i2v 파이프라인
- 분석 데이터: 운영 RDS `workflow_tasks` 109건(타이밍 보유 89건), `task_prompts` 111건, 운영 EFS 워크플로우 13개 — 2026-08-06 ~ 08-21
- 상세 설계: [A 성능](superpowers/specs/2026-08-30-runpod-performance-design.md) · [B·C 품질](superpowers/specs/2026-08-30-quality-and-template-governance-design.md)

---

## 1. 요약

성능 저하와 품질 저하를 각각 추정이 아니라 **운영 데이터로 원인을 확정**했습니다.

- **성능**: 체감 지연의 절반 이상이 GPU 연산이 아니라 **대기**였습니다. p90 기준 대기 497초 > 실행 470초. 작업을 몰아 넣을 때만 발생하며 유휴 콜드스타트는 원인이 아닙니다.
- **품질**: 사용자는 기본값을 거의 벗어나지 않습니다(97%). 따라서 **기본값과 상한 자체가 문제**입니다. 특히 26%가 모델 학습 윈도우(81프레임)의 2배인 161프레임을 요청하고 있습니다.
- **공통 구조**: 성능·품질·템플릿 세 영역이 모두 **"만들어 두고 측정하지 않는"** 같은 패턴이었습니다. 계측이 없어 원인을 몰랐고, 평가가 없어 무엇이 나쁜지 몰랐고, 검증이 없어 같은 결함을 복제하고 있었습니다.

즉시 조치 1건을 완료했고, 나머지는 3개 설계 문서로 정리했습니다.

---

## 2. 핵심 발견

### 2.1 성능 — 대기가 실행보다 길다

```
delay(대기)  p50=14.0s   p90=496.8s   p95=682.7s   max=3,971s
exec(실행)   p50=229.6s  p90=469.7s   p95=516.9s   max=541s
```

대기의 p50 → p75가 14초 → 356초로 **25배** 점프합니다. 원인은 직전 작업과의 간격으로 갈립니다.

| 직전 작업과의 간격 | 대기 중앙값 |
|---|---|
| **2분 미만** | **371.6초** |
| 2분 ~ 1일 | 10~12초 |
| **1일 이상** | **10.1초** |

**하루 넘게 놀린 엔드포인트도 10초 만에 시작합니다.** 유휴 콜드스타트는 문제가 아니며 FlashBoot는 정상 동작 중입니다. 긴 대기는 작업이 몰릴 때 신규 워커가 뜨면서 네트워크 볼륨에서 모델 30GB+를 다시 읽는 비용입니다.

**작업 실패율 16.5%(18/109)** 이며, 전부 실행 타이밍 기록이 없습니다 — 워커를 잡지 못하고 큐에서 만료된 것입니다. 13건은 2026-08-10 20초 사이에 몰린 단일 버스트였습니다.

### 2.2 성능 — GPU 편차는 예상보다 작았다

작업 조건을 정규화한 워커별 실행 속도 편차는 **1.56배**입니다.

> 초기 로컬 표본 5건으로는 3.8배로 보였으나, 운영 89건으로 확대하니 1.56배였습니다. **초기 수치는 표본 노이즈였고, 이 정정이 GPU 상향 투자 판단을 바꿉니다.**

다만 워커 **내부** 편차가 최대 3.1배로 워커 간 편차보다 크다는 미해결 관측이 남아 있습니다. 외부 검토는 24GB급 GPU에서 모델(22~28GB 요구)이 메모리를 넘겨 오프로딩이 발생한다는 가설을 제시했고, 사실이라면 GPU 상향 효과는 1.56배가 아니라 2~3배가 됩니다. **판별하려면 워커의 GPU 모델을 기록해야 하며, 현재는 그 정보를 수집하지 않습니다.**

### 2.3 품질 — 노브가 거꾸로 달려 있다

사용자 지목 증상: 움직임 부자연(`naturalMotion`), 형태 왜곡(`noDistortion`), 배경 불안정(`backgroundStable`). 프롬프트 반영(`intentMatched`)은 지목되지 않아 **프롬프트·LLM 경로는 정상**입니다.

| 원인 | 영향 범위 |
|---|---|
| **161프레임 요청** — 워크플로우 자체 기본값 81의 2배. 모델 학습 윈도우 초과 | **26%** (28건) |
| 해상도가 Wan 권장 비율과 어긋남 (720×720, 1248×720, 688×784 등 9종 혼용) | 다수 |
| `cfg` 1.8 / 3.9 — 4-step distilled LoRA는 1.0이 전제 | 3건 |
| `motionShift=1` — 선언 최소값 2.0 미만인데 통과. 권장 하한은 5.0 | 5건 |

**사용자는 97%가 기본값을 씁니다.** 그런데도 불만이 있다는 것은 범위 문제가 아니라 기본값·상한 자체가 잘못됐다는 뜻입니다. 그리고 이탈한 소수는 정확히 해로운 값에 착지했습니다 — **범위가 사용자를 잘못된 곳으로 안내하고 있습니다.**

근본 원인은 서버가 선언된 `min`/`max`를 전혀 검사하지 않는다는 점입니다. 브라우저가 유일한 게이트입니다.

### 2.4 템플릿 — 검증 없이 활성화되고, 결함이 복제된다

- 운영 워크플로우 **13개 중 7개가 등록·검증 이력이 없습니다.** 미등록 워크플로우는 기본값이 "활성"이라 자동 노출됩니다. **실행 1위(33건) 템플릿이 바로 이 경우입니다.**
- paramconfig 자동 생성기가 워크플로우의 스위치 분기를 이해하지 못해, **새 템플릿을 등록할 때마다 같은 함정을 복제**합니다. 최근 추가된 3개 템플릿에 그대로 전파됐습니다.
- `3~6-images` 4개 템플릿에서 최종 영상이 **1.5배 빠르게 재생되는 인코딩 결함**을 발견했습니다(세그먼트 16fps 생성 → 최종 24fps 인코딩).

### 2.5 측정 수단 자체가 없다

| 영역 | 현황 |
|---|---|
| 성능 지표 | RunPod 응답이 JSON 컬럼에 묻혀 있어 집계 불가. CloudWatch에는 실행 지표 없음 |
| 결과 품질 평가 | 채널·화면·API 모두 존재하나 **수집률 1.8%**(111건 중 2건, 둘 다 5점) |
| 템플릿 검증 | 노드 형식만 확인. 모델·노드 실재 여부는 미검증 |

이번 진단을 위해 운영 컨테이너에 직접 진입해야 했다는 사실이 이 문제를 그대로 보여줍니다.

## 3. 조치 현황

| 조치 | 상태 | 비용 |
|---|---|---|
| Execution Timeout 600초 → 1200초 | **완료 (08-30)** | 없음 (실사용 초 단위 과금) |
| Job TTL 상향 | 대기 | 없음 |
| Max Workers 7 → 10 (앱 정책과 일치) | 대기 | 유휴 시 없음 |
| Idle Timeout 상향 | 대기 | 없음 |

> Execution Timeout은 긴급했습니다. 최대 관측 실행 시간이 541초로 **한도 600초의 90%**였고, 워커 편차를 감안하면 곧 실패가 발생할 상태였습니다. 조치로 여유가 90% → 45%로 확보됐습니다.

## 4. 계획

3개 설계 문서로 정리했으며, 순서에 의존 관계가 있습니다.

### A. 성능
1. **콘솔 설정** — Job TTL, Max Workers, Idle Timeout (비용 없음)
2. **계측 구축** — 타이밍 지표 컬럼화, **워커 GPU 정보 수집**, 완료 무결성 검사, 관리자 화면 대기/실행 분리 표시
3. **볼륨 의존 제거** — 모델을 워커 이미지에 포함, 운영/샌드박스 볼륨 분리
4. **세그먼트 병렬화** — *3번 완료 후에만 착수* (조건부)

### B. 결과 품질
1. **서버측 범위 강제** — 이 하나가 아래 항목들을 실효화하는 키스톤
2. **paramconfig 값 교정** — cfg 1.0 고정, shift 하한 5.0
3. **해상도를 Wan 권장 비율로 정렬**
4. duration 경고 표시 (차단하지 않음)
5. **골든 테스트 세트** — 고정 seed 기반 회귀 검증
6. **프레임 보간(RIFE)** — 5초 생성 후 보간으로 길이 요구 흡수

### C. 템플릿 품질
1. **미등록 워크플로우 비활성화** (검증 통과 후 등록과 함께 배포)
2. **생성기를 fail-closed로** — 안전 범위를 증명할 수 없으면 잠금
3. **Workflow Release 도입** — 워크플로우·paramconfig·노드 버전·**모델 SHA-256**·기대 출력을 한 단위로 버전 관리

## 5. 결정이 필요한 사항

| # | 사안 | 선택지 | 현황 |
|---|---|---|---|
| 1 | 영상 길이 상한(10초) | 제한 / **경고만** / 잠정 제한 | **결정됨 — 경고만, 상한 유지** |
| 2 | 모델을 워커 이미지에 포함할 것인가 | 포함 / 볼륨 유지 / 부팅 시 로컬 복사 | **미결정.** 성능 개선폭이 가장 크나 샌드박스 환경 공유 방식을 바꿔야 함 |
| 3 | GPU 등급 상향 | 상향 / 현행 | **보류.** 계측으로 VRAM 가설을 판별한 뒤 결정 (1.56배 vs 2~3배) |
| 4 | 미사용 템플릿 2개 처리 | 유지 / 폐기 | **미결정.** `video_minimax_h3_r2v`, `flf2v` 모두 사용 0건. 단 flf2v는 병렬화 설계의 기반 |
| 5 | Staging 환경 신설 | 신설 / 태그로 경량 운영 | 경량 형태로 시작 권장 |

**2번이 가장 중요합니다.** 대기 시간 문제의 근본 해결책이면서, 동시에 "샌드박스와 볼륨을 공유해 환경을 맞춘다"는 현재 방식을 대체할 장치(Workflow Release)를 함께 갖춰야 하는 사안입니다.

## 6. 비용 영향

즉시 조치 가능한 항목은 **모두 추가 비용이 없습니다.** 서버리스는 실사용 시간 과금이라 타임아웃·워커 상한 조정은 유휴 비용을 늘리지 않습니다.

비용이 발생하는 선택지는 셋이며, 세 건 모두 **판단을 보류했습니다.**

| 항목 | 비용 | 판단 |
|---|---|---|
| Active Worker 상시 유지 | GPU 시간 상시 과금 | **권장하지 않음.** 유휴 콜드스타트가 문제가 아님이 데이터로 확인됨 |
| GPU 등급 상향 | 시간당 단가 증가 | 계측 후 재판단 (결정 3번) |
| Staging 엔드포인트 | 추가 엔드포인트 | 경량 형태로 시작 |

외부 검토 문서 일부가 Active Worker 상시 유지를 권했으나, **1일 이상 유휴 후에도 대기가 10초에 불과하다는 실측**에 따라 채택하지 않았습니다.

## 7. 남은 리스크

| 리스크 | 성격 |
|---|---|
| 워커의 조용한 실패가 성공으로 기록됨 | **확인됨.** 161프레임 작업이 0.9초 만에 "완료"로 저장된 사례. 계측 단계에서 무결성 검사 추가 |
| 81프레임 초과 구간의 품질 저하 | **수용됨.** 길이 상한 유지 결정에 따른 것이며, 프레임 보간(B-6)으로 해소 가능 |
| base64 전송 한도 | **조건부.** 현재 운영은 입력 1장(최악 5.3MB)이라 한도 10MB까지 여유. 입력 수·해상도를 늘리면 필수 과제화 |
| VRAM 오프로딩 가설 미검증 | 계측 전까지 GPU 투자 판단 불가 |

## 8. 참고

### 검토 방법
운영 데이터 직접 조회(읽기 전용), 워크플로우 JSON 전수 분석, 백엔드 코드 확인. 외부 검토 3건을 실측·코드와 대조해 채택·기각을 판별했습니다.

**기각한 주장 3건**을 근거와 함께 설계 문서에 기록했습니다 — 그대로 채택하면 손해를 보는 항목들입니다.

- "동시 워커를 2개로 축소" → 현재 7개에서도 큐 포화로 16.5%가 실패 중
- "기존 S3 저장소 활용" → 현재 EFS를 쓰며 S3는 미사용. 신규 구축 사안
- "상태 조회가 클라이언트 폴링" → 서버측 주기 폴링이 이미 존재
