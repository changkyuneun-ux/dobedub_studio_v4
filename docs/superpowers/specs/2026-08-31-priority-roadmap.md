# 우선순위 재편 로드맵

- 작성일: 2026-08-31
- **이 문서가 [A 성능](2026-08-30-runpod-performance-design.md)·[B·C 품질](2026-08-30-quality-and-template-governance-design.md) 스펙의 우선순위를 대체한다.** 두 스펙의 측정 결과와 기술 설계는 그대로 유효하며, 무엇을 먼저 할지는 이 문서를 따른다.
- 근거 분석: [작업 이력 분석](../../task-history-analysis-2026-08-31.md)

## 1. 재편 사유

운영 이력 109건 분석에서 두 가지가 확인됐고, 그 결과 기존 우선순위가 실제 문제와 어긋나 있었다.

**대기 시간의 89%가 동시 실행에서 나온다.** 대기가 60초를 넘은 37건 중 33건이 다른 작업이 실행 중일 때 제출됐다. 유휴 상태에서 제출한 경우는 24시간을 놀린 뒤에도 11초에 시작한다.

**따라서 Idle Timeout 상향은 효과가 없다.** 후보값별로 계산한 결과 300초로 잡으면 유휴 과금이 실제 실행 GPU 시간의 124%가 되는데 warm으로 바뀌는 제출은 0건이다. 이 항목은 폐기한다.

**실제 지렛대는 큐 관리다.** 동시 실행 수를 통제하고, 대기 상태를 사용자에게 보여주고, 워커 수를 그에 맞추는 것이 순서대로 효과가 크다.

## 2. 오늘 확정한 결정

| # | 사안 | 결정 |
|---|---|---|
| 1 | 동시 요청 통제 범위 | **워커 수만큼만 동시 허용.** 초과분은 앱 큐에서 시간순 대기 |
| 2 | Grok의 역할 | **병행.** 장면 기반 텍스트 프롬프트는 기존 Qwen 유지, 이미지 묘사 경로만 Grok |
| 3 | 영상 길이 옵션 | **81(기본) / 161(선택).** WAN latent 규칙 4n+1을 따른다. 160은 규칙에 어긋나 내부 보정된다 |

기존 결정 중 유지되는 것: 영상 길이 상한을 없애지 않는다(경고가 아니라 이산 선택으로 전환), `3~6-images` 템플릿은 비활성화한다.

## 3. 우선순위

### P1. 작업 Queue 관리 및 모니터링 강화

**목표** — 지금 몇 건이 밀려 있고 얼마나 기다려야 하는지 사용자와 운영자가 모두 볼 수 있게 한다.

2026-08-10의 악순환(첫 실패 → 27분 재시도 → 23초간 13건 일괄 제출 → 전부 만료)은 **얼마나 기다려야 하는지 모르는 상태**에서 시작됐다. 정보가 없으면 몰아넣는 것이 합리적 선택이 된다.

**할 일**
- 제출 화면에 큐 상태 노출 — 대기 건수, 실행 중 건수, 예상 대기 시간
- 관리자 화면에 대기(p50/p95)와 실행(p50/p95) **분리** 표시. 합산만 보면 원인이 보이지 않는다
- 타이밍 지표를 `workflow_tasks` 전용 컬럼으로 승격 — 현재 `runpod_status_json` 안에 묻혀 있어 집계가 불가능하다
- 실패 작업의 재시도 동선 — 수동 재제출 반복이 일괄 제출로 이어진다

**기존 문서** — A 스펙 Phase 1-1, 1-4, 1-5, 1-8

### P2. 시간순 대기 작업 관리

**목표** — 동시 실행 수를 워커 수 이하로 유지하고, 초과분은 앱이 시간순으로 대기시킨다.

**정책** — RunPod에 동시에 보내는 작업 수를 **가용 워커 수 이하**로 제한한다. 초과 제출은 거부하지 않고 앱 큐에 FIFO로 쌓았다가 자리가 나면 순서대로 보낸다.

이렇게 하면 RunPod 쪽에서 스케일아웃이 발생하지 않으므로 대기의 주원인이 사라지고, 큐 만료도 구조적으로 불가능해진다.

**기반** — `runpod_client.connection_status()`가 이미 `/health`에서 `workers`를 받아온다. 가용 워커 수를 설정값이 아니라 **실측으로** 구할 수 있다.

**기존 정책과의 관계** — `task_execution_policies`의 동시 활성 제한(사용자당 3 / 전체 10)은 *거부* 방식이다. P2는 *대기* 방식이므로 이를 대체한다. 전체 상한은 큐 길이 제한으로 남긴다.

**열린 항목**
- 큐 상태를 어디에 저장할 것인가 — DB 테이블 신설 vs `workflow_tasks`의 상태값 확장
- 워커 수를 매번 `/health`로 조회할지, 주기 캐시할지
- 앱 인스턴스가 늘어날 때의 큐 소유권 (현재 ECS 태스크 1개)

### P3. 워커 수 관리 및 워커별 모니터링

**목표** — 워커 수를 P2의 동시 허용치와 연동해 관리하고, 워커별 성능을 추적한다.

**할 일**
- `workflow_tasks`에 `runpod_worker_id` 컬럼 승격
- **워커 핸들러가 GPU 모델명과 VRAM을 output에 실어 보내게 한다.** RunPod API는 GPU 정보를 주지 않는다
- 워커별 정규화 실행 속도(`executionTime / (frames × 메가픽셀)`) 대시보드
- Max Workers 값과 P2의 동시 허용치 정합성 확인

**판별 대상 가설** — 워커 간 정규화 편차는 1.56배인데 워커 **내부** 편차가 최대 3.1배다. 24GB급 GPU에서 모델(22~28GB 요구)이 VRAM을 넘겨 오프로딩이 발생한다는 가설이 있다. **사실이면 GPU 등급 상향 효과가 1.56배가 아니라 2~3배가 되므로 투자 판단이 바뀐다.** GPU 모델명 수집 없이는 판별할 수 없다.

**기존 문서** — A 스펙 Phase 1-2, 1-5, 1-7

### P4. 서버리스 RunPod 배치 작업 연계

**목표** — 여러 작업을 하나의 배치로 묶어 제출하고 단위로 추적한다.

**P5와 짝을 이룬다.** P5가 이미지 N장에서 프롬프트 N개를 만들면 그 결과는 N건의 생성 요청이며, 이것이 곧 배치다. P2의 큐가 배치를 시간순으로 풀어 보내는 실행 계층이 된다.

```
P5 (이미지 N장 → 프롬프트 N개) → P4 (배치 단위 묶음) → P2 (큐가 순서대로 제출) → RunPod
```

**설계 필요** — 이 항목은 요구사항이 아직 구체화되지 않았다. 최소한 아래가 정해져야 한다.
- 배치의 단위와 식별자 (배치 ID, 소속 task 목록)
- 부분 실패 처리 — 10건 중 3건 실패 시 배치 상태를 무엇으로 볼 것인가
- 진행률 표시 단위 (배치 기준 vs 개별 작업 기준)
- 배치 취소 시 이미 실행 중인 작업의 처리

**별도 설계 문서가 필요하다.**

### P5. Grok API를 활용한 프롬프트 생성

**목표** — 입력 이미지 여러 장을 받아 각 이미지에 맞는 i2v 프롬프트를 생성하고, 이미지-프롬프트 쌍으로 생성 요청을 만든다.

**흐름**
```
이미지 N장 + Grok 시스템 프롬프트(md)
      ↓
Grok vision 호출 — 이미지별 묘사 → WAN i2v 프롬프트
      ↓
(이미지, 프롬프트) N쌍
      ↓
P4 배치 → P2 큐 → RunPod
```

**기반이 절반 있다** — `prompt_llm_client`에 `openai_compatible` provider 경로가 이미 있고 Grok(xAI) API는 OpenAI 호환이므로, base URL과 API 키만 바꾸면 텍스트 생성은 붙는다. 재시도 로직도 공유된다.

**새로 필요한 것**
- **Vision 입력 경로.** 현재 `generate()`는 `scene`/`constraints` 텍스트만 받는다. 이미지를 메시지에 실어 보내는 경로가 없다
- **Grok 시스템 프롬프트 관리.** 기존 `prompt_system_prompts` / `prompt_system_prompt_versions` 테이블에 이미지용 스코프를 추가하는 방향으로 검토한다. 새 저장소를 만들지 않는다
- 이미지-프롬프트 쌍의 보관과 재사용 — `task_prompts`가 이미 세그먼트별 프롬프트와 입력 자산을 연결하고 있어 확장 가능하다

**병행 결정** — 장면(Scene) 기반 텍스트 프롬프트 생성은 기존 RunPod Qwen을 유지한다. 두 경로가 공존하므로 provider 선택이 **호출 지점별**로 갈린다. 설정 하나로 전역 전환하는 현재 구조(`PROMPT_LLM_PROVIDER`)를 그대로 쓸 수 없다.

**별도 설계 문서가 필요하다.**

### P6. 워크플로우 모델 및 노드 설정값 관리

**목표** — 사용자가 만질 수 있는 값을 최소로 줄이고 나머지는 템플릿 초기값으로 잠근다.

| 값 | 정책 |
|---|---|
| **해상도** | 입력 이미지의 가로×세로에서 **계산해서 전달** |
| **fps** | **16 고정** |
| **length** | **81 기본 / 161 선택** |
| 그 외 전부 (`cfg`, `steps`, `shift`, `split_step`, `bit_depth`, `codec` …) | **조정 불가.** 템플릿 초기 설정값 유지 |

**이것이 B 트랙을 대체한다.** 기존 설계는 파라미터별로 안전 범위를 협상하려 했으나(cfg 1.0 고정, shift 하한 5.0, 해상도 프리셋 목록), **전부 잠그고 두 개만 여는** 쪽이 더 명확하고 구현도 단순하다.

**해상도 도출 규칙 — 설계 필요**

입력 이미지의 종횡비를 그대로 따르면 WAN 학습 범위를 벗어난다. 실제 업로드 표본에 `1280×530`(2.4:1)이 있다. 아래 순서로 도출한다.

1. 입력 이미지의 가로×세로를 읽는다
2. 종횡비를 WAN이 감당하는 범위로 클램프한다 (극단 비율 제한)
3. 픽셀 예산(`MAX_RESOLUTION_PIXELS = 1,048,576`) 안으로 스케일한다
4. 가로·세로를 각각 16의 배수로 스냅한다

**선행 조건** — `assets.image_width` / `image_height` 컬럼은 존재하나 **117건 중 14건만 채워져 있다.** 업로드 시점에 크기를 반드시 기록하도록 먼저 고쳐야 한다. Pillow는 이미 설치되어 있다.

**강제 수단** — `apply_node_config_to_workflow()`가 paramconfig의 `min`/`max`/`options`를 전혀 검사하지 않는다. 브라우저가 유일한 게이트다. **서버측 강제 없이는 잠금이 성립하지 않는다.** 이것이 P6의 첫 작업이다.

**기존 문서** — B·C 스펙의 B-1(서버측 강제)과 3.1(생성기 fail-closed 원칙)은 그대로 유효하다. B-2·B-3·B-4·B-6은 이 항목에 흡수된다.

**영향** — 현재 운영에서 `fps=15`로 실행된 5건(`2-images`, 45프레임)이 새 정책과 맞지 않는다. 해당 템플릿의 처리를 정해야 한다.

## 4. 기존 스펙과의 관계

| 기존 항목 | 처리 |
|---|---|
| A Phase 0 — Execution Timeout | **완료** (600s → 1200s, 08-30) |
| A Phase 0 — **Idle Timeout 상향** | **폐기.** 효과 0건, 유휴 과금만 증가 (1절) |
| A Phase 0 — Job TTL, Max Workers | P2·P3에 흡수. P2가 큐를 통제하면 만료 자체가 발생하지 않는다 |
| A Phase 0 — GPU 풀 정리 | P3에 흡수. GPU 모델명 수집 후 판단 |
| A Phase 1 — 계측 | P1·P3으로 분할 |
| A Phase 2 — 볼륨 의존 제거 | **유지, 후순위.** P2가 스케일아웃을 억제하면 긴급도가 내려간다 |
| A Phase 3 — 세그먼트 병렬화 | **유지, 조건부.** 현재 단일 세그먼트 작업이 대부분 |
| A Phase 4 — S3 입출력 | **유지, 조건부.** 현재 입력 1장이라 여유 있음. P4·P5로 입력이 늘면 재검토 |
| B-1 서버측 강제 | P6의 첫 작업 |
| B-2·B-3·B-4·B-6 | P6에 흡수 |
| B-5 프레임 보간(RIFE) | **보류.** 161을 정식 옵션으로 허용하므로 급하지 않다 |
| B-7 골든 테스트 세트 | **유지.** 평가 수집률 1.8%라 개선 효과 검증 수단이 여전히 없다 |
| C-1·C-2 미등록 비활성 | **유지.** 검증 없이 활성인 워크플로우 7개 |
| C-3 생성기 fail-closed | P6과 같은 방향. `locked`가 기본이 된다 |
| C-4 Workflow Release | **유지, 후순위** |

## 5. 다음 단계

**설계 문서가 필요한 것** — P4(배치 연계), P5(Grok 프롬프트 생성). 둘은 짝이므로 함께 설계한다.

**바로 구현 계획을 쓸 수 있는 것** — P6은 [기존 구현 계획](../plans/2026-08-30-parameter-enforcement.md)을 재정의하면 된다. 서버측 강제(Task 1·2)는 그대로 쓰고, paramconfig 교정(Task 3·4)을 "전부 잠금 + 해상도 도출"로 바꾼다.

**착수 순서 제약**
- P6의 잠금은 서버측 강제가 선행되어야 성립한다
- P6의 해상도 도출은 `assets.image_width` 기록이 선행되어야 한다
- P4는 P2의 큐가 있어야 실행 계층이 생긴다
- P5의 결과물은 P4의 입력이다

## 6. 열린 항목

- P2의 큐 저장 위치, 워커 수 조회 주기, 다중 앱 인스턴스 시 큐 소유권
- P4의 배치 단위·부분 실패·취소 정책
- P5의 provider 선택을 호출 지점별로 어떻게 가를 것인가 (전역 `PROMPT_LLM_PROVIDER`로는 불가)
- P6에서 `fps=15`를 쓰던 `2-images` 템플릿의 처리
- P6의 종횡비 클램프 범위 — WAN이 감당하는 최대·최소 비율을 실측으로 정해야 한다
- VRAM 오프로딩 가설 (P3에서 판별)
