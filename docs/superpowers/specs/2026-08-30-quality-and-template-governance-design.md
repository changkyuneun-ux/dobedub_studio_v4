# 결과 품질(B) · 워크플로우 템플릿 품질(C) 개선 설계

- 작성일: 2026-08-30
- 개정: 2026-08-30 — 외부 검토 3건(Cowork / Codex / Gemini) 대조 반영. 8장에 채택·기각 근거 기록.
- 범위: B(결과 품질)와 C(템플릿 품질). 둘은 뿌리를 공유하므로 한 스펙으로 묶는다. A(성능)는 [2026-08-30-runpod-performance-design.md](2026-08-30-runpod-performance-design.md) 참조.
- 근거 데이터: 운영 RDS `workflow_tasks` 109건, `task_prompts` 111건, 운영 EFS `WORKFLOWS_DIR` 13개 워크플로우, 리포지토리 워크플로우 JSON 전수


> **우선순위 안내 (2026-08-31)**: 이 문서의 측정 결과와 기술 설계는 유효하나, **무엇을 먼저 할지는 [우선순위 재편 로드맵](2026-08-31-priority-roadmap.md)을 따른다.** 특히 Idle Timeout 상향은 폐기됐고, 큐 관리가 최우선으로 올라왔다.

## 1. 공통 뿌리

paramconfig가 세 가지를 동시에 잘못하고 있다.

1. **위험한 노브를 연다** — 4-step distilled LoRA 분기에서 `cfg`를 12.0까지, `steps`를 50까지 노출한다.
2. **유용한 노브를 숨긴다** — `split_step`은 어느 템플릿에도 노출되지 않는다.
3. **선언한 범위를 지키지 않는다** — `min`/`max`가 서버에서 강제되지 않는다.

B의 증상과 C의 재생산이 모두 여기서 나온다. 따라서 개별 증상을 고치지 않고 이 구조를 고친다.

여기에 템플릿 자체의 결함(2.6)과 모델 능력 경계를 넘는 요청(2.3)이 겹친다.

## 2. 측정 결과

### 2.1 사용자는 기본값을 거의 벗어나지 않는다 (n=109)

| 파라미터 | 최빈값 | 이탈 사례 | 선언 범위 |
|---|---|---|---|
| `steps` | 4 (97%) | 15, 6, 5 | 4→24 / 4→50 |
| `cfgScale` | 1 (97%) | **1.8 (2건), 3.9 (1건)** | 1.0→6.0 / 1→12.0 |
| `motionShift` | ≈5 (96%) | **1 (5건)** | min 2.0 |
| `frames` | 81 (62%) | **161 (28건, 26%)** | duration 최대 10초 |
| `fps` | 16 (95%) | 15 (5건) | 8→30 |

읽어야 할 것은 두 가지다.

**기본값을 벗어나지 않는데도 품질 불만이 있다** → 범위 문제가 아니라 기본값·상한과 템플릿 자체의 문제다.

**이탈한 소수는 정확히 해로운 값에 착지했다** → 범위가 사용자를 잘못된 곳으로 안내하고 있다.

### 2.2 증상과 원인의 대응

사용자가 지목한 증상은 `naturalMotion`, `noDistortion`, `backgroundStable` 세 가지다. `intentMatched`는 지목되지 않았다 — **프롬프트 주입 경로와 LLM 생성 품질은 이 스펙의 범위가 아니다.**

| 증상 | 원인 | 영향 범위 |
|---|---|---|
| naturalMotion, backgroundStable | `frames=161`이 워크플로우 자체 기본값 81을 2배 초과 (2.3) | **26%** |
| noDistortion, backgroundStable | 해상도가 Wan 네이티브 비율과 어긋남 (2.4) | 다수 |
| noDistortion | `cfg` 1.8/3.9. 4-step distilled LoRA는 cfg=1.0이 전제 | 3건 |
| naturalMotion | `motionShift=1`. 선언 최소값 2.0 미만인데 통과. 권장 하한은 5.0 (2.5) | 5건 |
| naturalMotion | `split_step`이 2로 고정. `steps` 변경 시 high/low noise 배분이 깨짐 | 3건 (거의 미발현) |
| naturalMotion | **fps 불일치로 최종본이 1.5배 빠르게 재생 (2.6)** | **현재 0건** — 아래 주의 |

> 정정 기록: 초판에서 `split_step` 고정을 B의 핵심으로 지목했으나, 운영에서 `steps`를 변경한 작업이 3건뿐이라 실제 영향은 가장 작다. 우선순위를 영향 범위 순으로 재배치했다.

### 2.3 duration 상한이 모델 학습 윈도우를 넘긴다

워크플로우 자신의 기본값은 81프레임(5초)인데, paramconfig의 `duration_seconds` 상한 10초가 `floor(10×16+1) = 161`을 만든다. 모델의 학습 윈도우를 넘어서면 후반부에서 모션이 뭉개지고 배경이 표류한다.

**운영 26%(28건)가 161프레임이며, 특히 `Wan22_default`와 `Pickme_Workflow` 계열이 집중적으로 쓴다.** 사용자가 지목한 두 증상과 가장 넓게 겹치는 원인이다.

### 2.4 해상도가 Wan 네이티브 비율과 어긋난다 (신규)

운영 실측 해상도(55건 기록):

```
width  최빈 720(56%), 그 외 1264, 1248, 736, 688, 640, 752, 1216
height 최빈 1280(36%), 그 외 720, 736, 784, 1216, 1248, 1264
실제 조합: 720×720, 720×1280, 1264×736, 1248×720, 688×784, 736×1280, 640×1216, 1216×720, 752×1280
```

Wan DiT는 학습된 특정 비율(**1280×720, 720×1280, 832×480, 480×832**)에서 가장 일관되고 왜곡 없는 모션을 만든다. 운영에서 쓰이는 `1248×720`은 `1280×720`에 근접하지만 다르고, `720×720` 정사각과 `688×784`는 네이티브가 아니다.

`noDistortion`·`backgroundStable`과 직결된다.

### 2.5 shift 하한이 잘못 선언되어 있다

paramconfig는 `motion_shift`의 `min`을 2.0으로 선언한다. 그러나 Wan 14B의 권장 범위는 **5.0~8.0**이며, 운영 96%가 이미 5.0을 쓰고 있다. **선언된 하한 2.0 자체가 근거 없이 낮다.** 강제만 해서는 부족하고 값을 고쳐야 한다.

### 2.6 fps 불일치 — 확정 결함, 단 현재 증상의 원인은 아니다 (신규)

`3~6-images` 4개 템플릿에서 세그먼트는 16fps로 생성되는데 최종 `CreateVideo`가 **24fps로 인코딩**한다.

| 템플릿 | 세그먼트 CreateVideo | 최종 CreateVideo |
|---|---|---|
| 3-images | 16fps ×2 | **노드 229 = 24fps** |
| 4-images | 16fps ×3 | **노드 246 = 24fps** |
| 5-images | 16fps ×4 | **노드 263 = 24fps** |
| 6-images | 16fps ×5 | **노드 280 = 24fps** |

`3-images.json` 기준 경로가 확정된다:

```
140:8 (세그먼트1 프레임) ┐
                        ├─→ 133 ImageBatch ─→ 229 CreateVideo(fps=24)
228:227 (세그먼트2 프레임) ┘

세그먼트 개별 인코딩: 140:60 CreateVideo(fps=16), 228:214 CreateVideo(fps=16)
```

**최종본이 24/16 = 정확히 1.5배 빠르게 재생된다.** `1-images`/`2-images`는 최종 concat 노드가 없어 해당 없다.

> **기대 효과를 오해하지 말 것**: 운영 이력 109건에서 `3~6-images`는 **사용 0건**이다(사용된 것은 1-images 33건, Pickme 계열 27건, Wan22_default 17건, 2-images 5건, Blowbang1 2건). 사용자가 **앞으로도 이 템플릿들을 쓰지 않을 것임을 확인했다(2026-08-30).**
>
> **따라서 이 결함은 사용자가 현재 겪는 증상의 원인이 아니며, 고쳐도 체감 품질은 달라지지 않는다.** 이 사실이 아래 B-0의 처리 방향을 결정한다.

### 2.7 범위가 서버에서 강제되지 않는다

[workflow_patch_service.py:201-211](../../../backend/app/services/workflow_patch_service.py#L201-L211)의 `apply_node_config_to_workflow()`는 `param_spec`에서 `default`만 읽고 `min`/`max`/`step`/`options`를 검사하지 않는다. 브라우저가 유일한 게이트다.

`motionShift=1`(선언 최소 2.0 미만)이 5건 통과한 것이 실증이다. **paramconfig를 고쳐도 이 구멍이 남으면 무의미하다.**

### 2.8 품질 평가 채널은 있으나 비어 있다

```
task_prompts (영상 결과 평가)   : 111건 중 평가 2건 (1.8%), 둘 다 5점
prompt_feedback (프롬프트 품질) : 0건
```

평가 축(`noDistortion`, `intentMatched`, `naturalMotion`, `backgroundStable`), 저장소, API, 화면이 모두 존재한다. 쓰이지 않을 뿐이다. 실행 1위 `1-images.json` 33건 중 평가는 0건이다.

**A와 같은 패턴이다.** A는 계측이 없어 원인을 몰랐고 B는 평가가 없어 무엇이 나쁜지 모른다. 수집률을 올리거나 다른 측정 수단을 만들지 않으면 이 스펙의 개선 효과도 검증할 수 없다.

### 2.9 검증되지 않은 워크플로우가 기본 활성

```
workflow-registry.json 등록 : 6개
운영 WORKFLOWS_DIR 워크플로우 : 13개
→ 7개는 등록·검증 이력 없음
```

[admin_service.py:219-221](../../../backend/app/services/admin_service.py#L219-L221):

```python
def is_workflow_active(workflow_id: str) -> bool:
    item = workflow_registry_item(workflow_id)
    return bool(item.get("active", True))   # 미등록이면 True
```

`register_admin_workflow()`를 거치지 않은 워크플로우는 `validate_workflow_registration_payload()`도 통과한 적이 없는데 자동으로 활성화된다. **실행 1위 `1-images.json`(33건)이 이 경우다.** 검증 파이프라인은 admin 업로드 경로에만 존재하고 seed 경로는 그냥 통과한다.

### 2.10 생성기가 함정을 복제한다

| paramconfig | steps | cfg | split_step |
|---|---|---|---|
| 1~6-images | 4 → 24 | 1.0 → 6.0 | 미노출 |
| Blowbang1 / Pickme_Workflow | 4 → 50 | 1 → 12.0 | 미노출 |
| **Wan22_default / Pickme_v3 / Pickme_v5** | 4 → 50 | 1 → 12.0 | 미노출 |
| video_wan2_2_flf2v | 20 → 50 | 4 → 12.0 | 미노출 |

굵게 표시한 셋은 리포지토리에 없는, admin으로 새로 등록된 템플릿이다. `generate_param_config()`가 `ComfySwitchNode` 분기를 이해하지 못해 **등록할 때마다 같은 함정을 재생산한다.**

## 3. 설계 원칙

### 3.1 생성기를 fail-closed로 뒤집는다

현재 `generate_param_config()`는 안전한 범위를 증명할 수 없는 파라미터에도 범위를 **지어낸다**(4→50). 이것이 C의 핵심 결함이다.

원칙을 뒤집는다: **증명할 수 없으면 잠근다.** 생성기는 스위치 분기를 거치거나 distilled LoRA 경로에 연결된 파라미터를 `locked: true`로 표시하고 `default`만 남긴다. 사람이 검토해 범위를 명시하고 잠금을 풀기 전까지 사용자에게 편집 불가로 보인다.

이 원칙 하나가 B의 cfg/shift 문제와 C의 재생산 문제를 동시에 닫는다.

### 3.2 템플릿을 "파일"이 아니라 "릴리스"로 다룬다

현재 Studio는 등록된 JSON만 저장한다. 그 JSON이 어떤 환경에서 검증되었는지, 어떤 모델 파일을 전제하는지, 무엇을 출력해야 정상인지에 대한 기록이 없다. C의 모든 증상이 여기서 파생된다.

**Workflow Release**를 도입한다. 하나의 릴리스는 아래를 함께 묶는다.

```
workflow JSON hash
paramconfig hash
ComfyUI / custom node 버전
모델 파일명 + SHA-256 + 경로
GPU / CUDA / Torch 정보
대표 입력 이미지 3~5장
고정 seed
기대 출력: 해상도, frames, fps, codec
```

모델을 파일명이 아니라 **SHA-256**으로 식별하는 것이 핵심이다. "파일명은 같지만 다른 모델" 문제를 잡는 유일한 방법이고, A 스펙 Phase 2(모델 베이크)가 볼륨 공유라는 환경 동기화 장치를 걷어낼 때 그 자리를 대신할 장치다.

## 4. B — 결과 품질

### B-0. fps 불일치 — 수정이 아니라 비활성화로 처리
`3~6-images`는 운영 사용 0건이고 앞으로도 쓰지 않는 템플릿이다(2.6). **결함이 있는 템플릿을 고쳐서 유지하는 대신, 활성 목록에서 내린다.**

이 템플릿들은 레지스트리에 등록된 적이 없으므로 **C-1(미등록 = 비활성)이 적용되면 자동으로 비활성화된다.** 별도 작업이 필요 없다. C-2가 seed 워크플로우를 레지스트리에 등록할 때 이 넷은 `active=false`로 등록한다.

**재활성화 시 선행 조건**으로 남긴다: 최종 `CreateVideo` fps를 24 → 16으로 맞추고(리포지토리·운영 EFS 양쪽), B-7 골든 세트를 통과해야 한다.

> 판단 근거: 고치는 비용 자체는 숫자 하나로 작다. 그러나 쓰지 않는 템플릿 4개를 활성 상태로 유지하면 A 스펙 2.8의 페이로드 위험(최악 15.9~31.8MB)과 이 fps 결함을 계속 안고 가야 하고, 앞으로의 모든 변경(B-1~B-3, C-3)이 이 넷에도 적용·검증되어야 한다. **유지 비용이 수정 비용보다 크다.**

### B-1. 서버측 범위 강제 (키스톤)
`apply_node_config_to_workflow()`에서 값을 노드에 주입하기 전에 `param_spec`의 `min`/`max`/`options`를 검사한다. 위반 시 `ValueError`를 던진다 — [jobs.py:29](../../../backend/app/api/v1/jobs.py#L29)가 이미 HTTP 400으로 변환한다.

- **클램프가 아니라 거부**한다. 조용한 보정은 사용자 의도를 숨긴다.
- `locked: true`인 파라미터는 `default` 외의 값을 거부한다.
- `step`(16의 배수 등)은 기존 `validate_segment_resolution()`이 담당하므로 중복 구현하지 않는다.

이 변경 하나로 B-2가 코드 수정 없이 데이터 수정만으로 실효화된다.

### B-2. paramconfig 값 교정 (데이터)
- `cfg_scale`: distilled LoRA 분기를 쓰는 템플릿에서 `min=max=default=1.0`으로 고정한다.
- `steps`: LoRA의 스텝 수로 고정한다.
- `motion_shift`: **`min`을 2.0 → 5.0으로 올린다** (2.5). 강제만으로는 부족하고 선언값 자체가 틀렸다.

대상은 운영 EFS의 13개 paramconfig다. 리포지토리 사본과 운영 EFS 사본을 **모두** 고쳐야 한다 — 앱 시작 시 기본본은 존재하지 않는 파일만 복사하므로 리포지토리만 고치면 운영에 반영되지 않는다.

### B-3. 해상도를 Wan 네이티브 비율로 정렬
입력 이미지를 임의 리사이즈하지 않고, 원본 비율에 가장 가까운 Wan 권장 해상도(1280×720, 720×1280, 832×480, 480×832)로 오토 패딩/크롭한다. paramconfig의 `width`/`height`는 자유 입력 대신 권장 조합 목록(`options`)으로 바꾼다 — B-1의 `options` 검사가 그대로 강제한다.

경계: 업스케일은 이 항목에 포함하지 않는다.

### B-4. duration 경고 (기능 유지)
`frames > 81`일 때 생성 화면에 품질 저하 경고를 표시한다. **차단하지 않는다.**

> 결정 근거: 운영 26%가 이 영역을 쓰고 있어 차단은 기존 워크플로를 깨뜨린다. 사용자가 기능 유지를 선택했다.
> **남는 위험**: B-5가 적용되기 전까지 81프레임 초과 구간의 `naturalMotion`/`backgroundStable` 저하는 해결되지 않는다.

### B-5. 프레임 보간으로 길이 요구를 흡수 (신규)
81프레임(5초)으로 생성한 뒤 `ComfyUI-Frame-Interpolation`(RIFE) 노드로 16fps → 30/60fps로 보간한다.

**B-4에서 수용하기로 한 남는 위험을, 기능을 줄이지 않고 해소하는 항목이다.** 모델의 학습 윈도우 안에서 생성하므로 모션·배경이 안정되고, 길이와 부드러움은 보간이 담당한다. 확산 모델로 프레임을 더 뽑는 것보다 연산도 훨씬 싸다.

전제: 서버리스 워커 이미지에 해당 custom node가 설치되어야 한다. **C-4의 검증 체계가 이 전제를 확인해 주는 첫 사례가 된다.**

경계: 이 항목은 duration 상한 정책을 바꾸지 않는다. 161프레임 직접 생성 경로는 그대로 두고, 보간 경로를 **선택지로** 추가한다. 어느 쪽이 기본이 될지는 B-7의 골든 세트 비교 결과로 정한다.

### B-6. split_step 파생
`split_step`을 2 고정에서 `steps`로부터 파생(`round(steps/2)`)하도록 바꾼다. 영향 범위가 가장 작으므로(3건) 후순위다.

### B-7. 골든 테스트 세트 (측정 수단)
워크플로우마다 회귀 테스트 세트를 만든다.

```
대표 입력 이미지 3~5장 / 고정 seed / positive·negative prompt
기대 출력: 해상도, frames, fps, codec
필수 모델 및 노드 버전
사람 검수 항목: noDistortion, naturalMotion, backgroundStable, intentMatched
```

구조값(해상도·frames·fps·codec)은 자동 검증하고, 지각 품질만 사람이 본다. **사용자 평가 수집률(1.8%)에 의존하지 않고 회귀를 잡을 수 있다는 점이 핵심이다.**

이것이 3.2 Workflow Release의 검증 절차이며, B의 개선 효과를 판정하는 유일한 신뢰 가능한 수단이다.

### B-8. 사용자 평가 수집률 개선
작업 완료 시점에 평가 진입 동선을 만들고, 미평가 작업을 이력 화면에서 구분 표시한다.

경계: 평가를 **강제하지 않는다**. 강제는 무성의한 5점을 만들어 데이터를 오염시킨다. B-7이 있으므로 이 항목은 보조 수단이다.

## 5. C — 템플릿 품질

### C-1. 미등록 워크플로우를 비활성으로
`is_workflow_active()`의 기본값을 `True` → `False`로 바꾼다. 검증을 통과한 적 없는 워크플로우가 사용자에게 노출되지 않는다.

**선행 조건**: 이 변경만 먼저 배포하면 현재 활성 워크플로우 7개가 즉시 사라진다. C-2를 먼저 끝내고 함께 배포한다.

### C-2. seed 경로도 검증 통과
`bootstrap_workflow_store()`가 seed에서 복사한 워크플로우도 등록·검증 파이프라인을 통과시켜 레지스트리에 기록한다. C-1의 선행 조건이다.

**활성 여부는 자동이 아니라 명시적 결정이다.** 등록은 하되 `active`는 실제 사용 이력을 근거로 정한다:

| 워크플로우 | 운영 사용 | 등록 시 active |
|---|---|---|
| 1-images | 33건 | `true` |
| Pickme_Workflow (+ v2/v3/v5) | 27건 | `true` |
| Wan22_default | 17건 | `true` |
| 2-images | 5건 | `true` |
| Blowbang1 | 2건 | `true` |
| **3-images / 4-images / 5-images / 6-images** | **0건** | **`false`** (B-0) |
| video_minimax_h3_r2v / video_wan2_2_flf2v | 0건 | 사용 계획 확인 후 결정 |

### C-3. 생성기의 스위치 분기 인식
`generate_param_config()`가 `ComfySwitchNode`를 추적해, 스위치를 거치는 파라미터를 3.1 원칙대로 `locked: true`로 표시한다. 비활성 분기의 노드는 아예 노출하지 않는다.

경계: 어느 분기가 "옳은지" 판단하지 않는다. 생성기는 **불확실성을 표시할 뿐** 값을 정하지 않는다.

### C-4. Workflow Release 도입
3.2의 릴리스 단위를 실제 자료구조로 만든다. `workflow-registry.json`의 항목을 릴리스 레코드로 확장하고, 등록 시 아래를 채운다.

- workflow JSON / paramconfig 해시
- 워커에서 조회한 `object_info` 스냅샷과 대조한 custom node 목록 및 버전
- 참조 모델의 파일명 + **SHA-256** + 경로
- B-7 골든 세트 참조와 최근 실행 결과

`validate_workflow_registration_payload()`가 현재 확인하는 것은 노드가 dict인지, `class_type`이 있는지, `LoadImage`/`SaveVideo` 존재 여부뿐이다. 여기에 **미설치 `class_type`과 볼륨에 없는 모델 파일을 등록 시점에** 잡는 검사를 추가한다.

전제: `metadata_loader`에 `object_info` 스냅샷 경로가 이미 있으나 현재 `hasObjectInfoSnapshot: false`다. 서버리스 워커에서 `object_info`를 받아 스냅샷하는 단계가 선행되어야 한다.

### C-5. Staging 검증 후 승인
릴리스는 Staging 엔드포인트에서 B-7 골든 세트를 통과한 뒤에만 Production에서 활성화한다. 품질 저하 시 이전 릴리스로 롤백한다.

경계: Staging 엔드포인트 신설은 비용을 수반한다. 초기에는 **동일 엔드포인트에 릴리스 태그로 구분**하는 경량 형태로 시작하고, 필요가 확인되면 분리한다.

### C-6. 운영 볼륨과 샌드박스 볼륨 분리
현재는 샌드박스에서 모델을 옮기거나 custom node를 수정하면 운영 중인 서버리스가 실시간으로 깨진다. 운영 볼륨을 분리하고 read-only 원칙을 적용한다.

**A 스펙 Phase 2(볼륨 의존 제거)와 같은 작업이다.** 두 스펙이 같은 지점에서 만나며, 환경 동기화를 볼륨 공유 대신 C-4의 릴리스 매니페스트가 담당하게 되는 전환이다.

## 6. 구현 순서

의존 관계상 이 순서를 지킨다.

```
1. B-1 (서버측 강제)          ← 키스톤. 단독 배포 가능
2. B-2 (paramconfig 교정)     ← B-1이 있어야 효과 발생
3. B-3 (해상도 네이티브 정렬)   ← B-1의 options 검사 활용
4. B-4 (duration 경고)        ← 독립
5. C-2 → C-1 (검증 통과 후 기본 비활성)  ← 반드시 함께 배포
                              └ B-0(3~6-images 비활성)이 여기서 함께 처리됨
6. C-3 (생성기 fail-closed)
7. B-7 (골든 세트)            ← 이후 항목의 판정 수단
8. B-5 (프레임 보간)          ← B-7로 161프레임 직접 생성과 비교 판정
9. C-4 (Workflow Release)    ← A Phase 2의 선행 조건
10. C-6 (볼륨 분리)          ← A Phase 2와 동일 작업
11. B-8 (평가 수집률), B-6 (split_step), C-5 (Staging)
```

**B-1~B-3이 사용자가 보고한 증상에 직접 대응하는 유일한 구간이다.** 나머지는 재발 방지와 측정 체계다. 체감 개선을 먼저 확인하려면 1~3까지 배포하고 B-7 이전에 한 번 끊는 것이 좋다.

## 7. 검증 기준

B의 효과는 측정 수단이 있어야 검증된다. B-7(골든 세트)이 그 수단이고, B-8(사용자 평가)은 보조다.

**1단계 — 즉시 확인 가능 (B-0~B-3, C-1~C-3 배포 직후)**

| 지표 | 현재 | 목표 |
|---|---|---|
| 최종 CreateVideo fps ≠ 세그먼트 fps 인 **활성** 템플릿 | 4개 | 0개 (비활성화로 달성) |
| 선언 범위를 벗어난 값의 제출 성공 | 통과함 (shift=1, 5건) | 0건 (HTTP 400) |
| Wan 비네이티브 해상도 제출 | 다수 | 0건 |
| 레지스트리 미등록 활성 워크플로우 | 7개 | 0개 |
| 신규 등록 템플릿의 `locked` 미표시 스위치 파라미터 | 전부 | 0개 |

**2단계 — B-7 골든 세트 가동 후**

| 지표 | 현재 | 목표 |
|---|---|---|
| 골든 세트 구조값 자동 검증 통과율 | 측정 불가 | 100% |

**3단계 — 사용자 평가 30건 이상 축적 후**

| 지표 | 현재 | 목표 |
|---|---|---|
| 결과 평가 수집률 | 1.8% (2/111) | > 30% |
| `naturalMotion` / `noDistortion` / `backgroundStable` 위반 비율 | 측정 불가 | 기준선 확보 후 설정 |

## 8. 테스트

- **B-0**: **활성** 워크플로우 전수에 대해 최종 `CreateVideo.fps`가 세그먼트 fps와 일치하는지 검사. 상시 회귀 테스트로 두어, 불일치 템플릿이 활성화되면 실패하게 한다 — 재활성화 시 선행 조건을 코드로 강제하는 장치다.
- **B-1**: `min` 미만, `max` 초과, `options` 밖의 값, `locked` 파라미터의 비기본값 → 각각 `ValueError`. 범위 내 값과 `default` 생략 시 기존 동작 회귀 없음.
- **B-2**: 교정된 paramconfig로 `cfg=1.8`, `shift=2.0` 제출 시 거부. `cfg=1.0`, `shift=5.0` 통과.
- **B-3**: 비네이티브 해상도 조합 거부, 권장 조합 통과.
- **B-4**: `frames=161`에 경고 표시, 제출은 성공.
- **C-1/C-2**: seed 워크플로우가 부트스트랩 후 레지스트리에 기록되고 활성. 레지스트리에 없는 임의 파일은 비활성.
- **C-3**: `ComfySwitchNode`를 거치는 파라미터가 `locked: true`로 생성. 비활성 분기 노드 미노출. `1-images.json`을 입력으로 회귀 테스트.
- **C-4**: 모델 SHA-256 불일치 시 등록 거부. `object_info`에 없는 `class_type` 검출.

기존 `backend/tests/` 패턴을 따른다.

## 10. 범위 밖

- **프롬프트 생성 품질** — `intentMatched`가 증상으로 지목되지 않았다. `prompt_feedback` 0건도 이 스펙에서 다루지 않는다.
- **성능 항목** — 세그먼트 병렬화, 모델 베이크, S3 입출력은 A 스펙 소관이다.

## 11. 열린 항목

- `motionShift=1`이 어떤 경로로 들어왔는지 특정하지 못했다. 프론트 검증 누락인지, 구버전 paramconfig인지, API 직접 호출인지. B-1이 결과적으로 막지만 원인은 미확인이다.
- distilled LoRA 분기를 생성기가 자동 판별하는 휴리스틱(lora 파일명 패턴 등)은 C-3에서 시도하되, 판별 실패 시 `locked`로 남기는 것이 안전 기본값이다.
- B-5(RIFE)의 custom node가 현재 서버리스 워커 이미지에 설치되어 있는지 미확인. C-4의 `object_info` 스냅샷이 확보되면 즉시 판정된다.
- ~~`3~6-images`가 운영에서 거의 쓰이지 않는 이유 미확인~~ → 2026-08-30 사용자 확인으로 해소. 사용자가 선택하지 않는 것이며, 앞으로도 쓰지 않는다. B-0의 처리 방향(수정 대신 비활성화)이 여기서 나왔다.
- `video_minimax_h3_r2v`와 `video_wan2_2_14B_flf2v_2-images-1`도 운영 사용 0건이다. 사용 계획을 확인해 C-2의 등록 시 `active` 값을 정해야 한다. 특히 flf2v 템플릿은 A 스펙 Phase 3(세그먼트 병렬화)의 기반으로 지목된 것이라 폐기 여부에 성능 설계가 걸려 있다.
