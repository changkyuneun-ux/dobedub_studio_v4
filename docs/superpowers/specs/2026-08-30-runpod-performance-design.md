# RunPod Serverless i2v 성능 개선 설계 (A)

- 작성일: 2026-08-30
- 개정: 2026-08-30 — 외부 검토 3건(Cowork / Codex / Gemini) 대조 반영. 7장에 채택·기각 근거 기록.
- 범위: **A(성능)만.** B(결과 품질)와 C(템플릿 품질)는 [2026-08-30-quality-and-template-governance-design.md](2026-08-30-quality-and-template-governance-design.md) 참조.
- 근거 데이터: 운영 RDS `workflow_tasks` 109건 (타이밍 보유 89건), 2026-08-06 ~ 2026-08-21

## 1. 배경

사용자가 서버리스 i2v 작업의 성능 저하를 보고했다. 원인을 추정하지 않고 운영 데이터로 확정했다.

측정 경로: ECS Exec으로 운영 컨테이너에 진입해 `workflow_tasks`를 읽기 전용 조회했다. CloudWatch(`/aws/ecs/default/dobedub-app-cf8b`)에는 RunPod 실행 지표가 없다 — uvicorn 액세스 로그뿐이다. `delayTime`/`executionTime`/`workerId`는 `runpod_status_json` JSON 컬럼 안에만 존재해 집계가 불가능했고, 이 사실 자체가 Phase 1의 근거다.

## 2. 측정 결과

### 2.1 분포

```
n = 89 (타이밍 보유)

delay(s)   p50=14.0   p75=355.5   p90=496.8   p95=682.7   max=3971.1
exec(s)    p50=229.6  p75=310.0   p90=469.7   p95=516.9   max=540.6
total(s)   p50=403.4              p90=742.4   p95=872.6   max=4114.7

상태 (109건): COMPLETED 87 / TIMED_OUT 18 / FAILED 2 / CANCELLED 2
```

`delay`의 p50 → p75가 14초 → 356초로 25배 점프한다. **p90 기준 대기(497s)가 실행(470s)보다 길다.** 체감 지연의 절반 이상이 GPU 연산이 아니라 대기다.

### 2.2 대기의 원인: 유휴 콜드스타트가 아니라 스케일아웃

직전 작업과의 간격별 `delay` 중앙값:

| 간격 | n | delay 중앙값 | 10초 미만 비율 |
|---|---|---|---|
| < 2분 | 16 | **371.6s** | 6.2% |
| 2~10분 | 30 | 12.2s | 40.0% |
| 10~60분 | 25 | 10.3s | 48.0% |
| 1~24시간 | 14 | 11.6s | 35.7% |
| 1일 이상 | 3 | **10.1s** | 33.3% |

하루 넘게 유휴 상태였던 엔드포인트도 10초 만에 시작한다. **FlashBoot/warm pool은 정상 동작 중이며, 유휴로 인한 콜드스타트는 문제가 아니다.**

긴 대기는 작업을 몰아 넣을 때만 발생한다. `<2분` 그룹의 대기 372초는 실행 중앙값 230초보다 크다 — 단순히 앞 작업을 기다린 것이라면 230초 근처여야 한다. 초과분은 **신규 워커 스케일아웃 비용**이며, 워커가 새로 뜰 때마다 네트워크 볼륨(NFS)에서 WAN 2.2 i2v 모델 세트(high/low noise 14B fp8 2개 + LoRA + VAE + umt5 CLIP, 합계 30GB+)를 다시 읽는 데서 온다.

**메커니즘 보강(외부 검토 반영)**: 여러 워커가 동시에 뜨면 네트워크 볼륨의 대역폭이 포화되어 모델 로딩 속도가 함께 떨어진다. 즉 스케일아웃 비용은 워커 수에 선형이 아니라 그보다 나쁘게 증가한다. 이 사실은 3.1의 Max Workers 상향 효과와 4.2의 병렬화 순서에 직접 영향을 준다.

### 2.3 GPU 혼재는 부차적 요인 — 단, 미검증 가설이 하나 남는다

`executionTime`을 `frames × 메가픽셀`로 정규화한 워커별 중앙값:

```
최속   ot4nmw4dc7hijt  2444.8 ms/(frame·MP)   n=7   (내부 범위 1160.5 ~ 3595.4)
최저속 lemd2axaxlyyq3  3811.0 ms/(frame·MP)   n=5   (내부 범위 3421.7 ~ 5820.4)
→ 워커 간 중앙값 편차 1.56배
```

> 정정 기록: 초기 로컬 표본 5건에서 "GPU 편차 3.8배"로 판단했으나, 운영 89건 정규화 결과 1.56배다. 초기 수치는 표본 노이즈였다.

**미검증 가설(VRAM 오프로딩)**: 워커 **내부** 편차가 최대 3.1배(`ot4nmw4dc7hijt`: 1160.5 ~ 3595.4)로 워커 간 편차보다 크다. 본 문서는 이를 워크플로우·해상도 차이로 설명했으나, 외부 검토는 다른 설명을 제시한다 — WAN 2.2 14B fp8은 UNET 2개 + UMT5 XXL(~5GB) + VAE + latent를 합쳐 22~28GB를 요구하므로 24GB급 GPU에서는 CPU RAM ↔ VRAM 오프로딩이 발생해 추론이 2~3배 급증한다는 것이다.

두 설명은 배타적이지 않으며, 어느 쪽이든 **워커의 GPU 모델을 알아야 판별된다.** 이것이 Phase 1-2의 우선순위를 올리는 이유다. 가설이 사실이면 GPU 등급 상향의 기대 효과는 1.56배가 아니라 2~3배가 된다.

### 2.4 관측된 TIMED_OUT 18건은 큐 만료

```
TIMED_OUT 18건 중 delay/exec 기록 보유 : 0건
frames 분포 : 81프레임 16건, 161프레임 2건
날짜        : 08-06 2건, 08-07 1건, 08-10 15건 (그중 13건이 10:48~10:49 20초 버스트)
```

타이밍이 하나도 없다는 것은 **실행을 시작하지 못했다**는 뜻이다. 게다가 대부분이 81프레임짜리 빠른 작업(실행 중앙값 230초)이다. 실행이 길어 잘린 것이 아니라 워커를 확보하지 못하고 큐에서 만료됐다. Max Workers가 7이므로 13건 버스트에서 6건이 즉시 초과였다.

**만료 주체 특정(외부 검토 반영)**: RunPod 엔드포인트에는 실행 시간을 제한하는 Execution Timeout과 별개로 **큐 대기를 포함한 Job TTL**이 있다. 타이밍 없는 만료는 이 TTL에 걸린 것이다. 초판에서 "어떤 TTL인지 특정하지 못했다"고 남긴 열린 항목이 해소되었다.

### 2.5 Execution Timeout 600s: 미발현 위험 — **조치 완료**

```
exec > 400s : 17건 / 89건 (19.1%)
최대 관측    : 540.6s = 타임아웃의 90.1%, 여유 59.4초
```

상위 5건에 워커 편차 1.56배를 적용하면 811~843초로 600초 한도를 넘긴다. 이 원인으로 실패한 기록은 아직 없었다(2.4 참조).

> **2026-08-30 조치 완료**: Execution Timeout을 600s → 1200s로 상향했다.

### 2.6 설정 불일치

`task_execution_policies`: `maxActiveTasksTotal = 10`, `maxActiveTasksPerUser = 3` (2026-08-12 설정, 08-10 버스트 이후 도입).
엔드포인트 `Max Workers = 7`.

**앱이 동시 10건을 수락하지만 7개만 실행된다.** 초과 3건은 항상 대기하거나 만료된다.

### 2.7 완료 무결성 구멍

`task_20260806_061442_b79bb7` — 161프레임 작업이 `executionTime=905ms`로 **COMPLETED** 저장됐다. 물리적으로 불가능하며, 워커의 조용한 실패를 앱이 성공으로 기록했다. `poll_runpod_job()`은 RunPod의 `status` 문자열만 신뢰하고 산출물 유무나 실행시간 타당성을 검사하지 않는다.

### 2.8 base64 페이로드 — 현재 사용 범위에서는 여유가 있다 (신규)

`build_runpod_payload()`는 입력 이미지를 base64로 인코딩해 `/run` 본문에 싣는다. RunPod `/run`의 본문 한도는 10MB다. 운영 자산 실측(n=66)은 중앙값 0.81MB, 최대 3.98MB이며 base64는 ×1.33이다.

템플릿별 노출도:

| 템플릿 | LoadImage | 최악 | 중앙값 | 운영 사용 |
|---|---|---|---|---|
| 1-images / Pickme_Workflow / Blowbang1 | 1 | 5.3MB | 1.1MB | **61건** |
| 2-images | 2 | **10.6MB** | 2.2MB | 5건 |
| 3-images ~ 6-images | 3~6 | 15.9~31.8MB | 3.2~6.5MB | **0건** |

**운영에서 실제 쓰인 템플릿은 전부 입력 이미지 1장이므로 현재 한도까지 여유가 크다.** 2-images만 최악의 경우 10.6MB로 한계에 걸치지만 5건에 불과하고 중앙값 기준으로는 2.2MB다. 3~6-images는 한도를 크게 넘기지만 운영 사용이 0건이고, 사용자가 앞으로도 쓰지 않을 것임을 확인했다.

> 정정 기록: 초판에서 이를 "산술적으로 확정된 리스크"로 적었으나, 그 계산은 운영에서 쓰이지 않는 6-images를 기준으로 한 것이었다. 실제 사용 분포를 반영하면 **현재는 발현되지 않는 조건부 위험**이다.

따라서 이 항목은 아래 조건이 생길 때 착수한다.
- Phase 3(병렬화)로 세그먼트를 분리 제출하며 입력 이미지 수가 늘어날 때
- 해상도를 상향할 때
- 다중 입력 템플릿을 운영에 다시 투입할 때

### 2.9 세그먼트가 한 job 안에서 직렬 실행된다 (신규)

`N-images` 템플릿은 세그먼트 전부를 **하나의 job**에서 순차 실행한다:

| 템플릿 | 노드 수 | KSamplerAdvanced | 세그먼트 |
|---|---|---|---|
| 3-images | 38 | 4 | 2 |
| 4-images | 56 | 6 | 3 |
| 5-images | 74 | 8 | 4 |
| **6-images** | **92** | **10** | **5** |

`KSamplerAdvanced`가 세그먼트당 2개(high/low noise)이므로 6-images는 샘플링만 10회를 직렬로 돈다. **생성 시간이 세그먼트 수에 비례하며, 워커를 늘려도 단일 작업은 전혀 빨라지지 않는다.** 각 세그먼트는 독립적인 i2v이므로 병렬화 가능한 구조다.

## 3. 설계

### 3.1 Phase 0 — RunPod 콘솔 (코드 변경 없음)

| 설정 | 현재 | 목표 | 근거 |
|---|---|---|---|
| Execution Timeout | ~~600s~~ **1200s** | — | 2.5. **조치 완료** |
| **Job TTL** | 미확인 | 큐 대기 + 실행 시간을 포괄 | 2.4. 타이밍 없는 TIMED_OUT 18건의 직접 원인 |
| Max Workers | 7 | **10** (단서 아래) | 2.6. 앱 정책과 일치시킨다 |
| Idle Timeout | 미확인 | 60~120s 이상 | 2.2. 연속 제출 시 워커 재사용으로 30GB 재로딩 회피 |
| GPU 풀 | 혼재 | 최저속 등급 제외 | 2.3. **기대 효과 1.56배.** VRAM 가설이 사실이면 재산정 |

**Max Workers 상향의 단서**: 2.2의 볼륨 대역폭 포화 때문에 워커를 늘려도 선형으로 개선되지 않는다. 10으로 올린 뒤 `delay` p90을 재측정해 실제 개선폭을 확인하고, 개선이 미미하면 병목이 워커 수가 아니라 볼륨임이 확인되는 것이므로 Phase 2를 앞당긴다.

### 3.2 Phase 1 — 앱 계측

**1-1. 타이밍 지표 컬럼 승격**
`workflow_tasks`에 `runpod_delay_ms`, `runpod_execution_ms`, `runpod_worker_id` 컬럼을 추가한다. alembic 마이그레이션 1장(기존 `backend/app/db/migrations/versions/` 패턴). `poll_runpod_job()`이 terminal 상태 도달 시 `runpod_status_json`에서 읽어 채운다. 기존 JSON 컬럼은 원본 보존용으로 유지한다.

경계: 쓰기 경로만 바꾼다. 과거 행의 백필은 하지 않는다 — `runpod_status_json`에 원본이 남아 있어 필요 시 별도 스크립트로 가능하다.

**1-2. GPU 모델 확보 — 우선순위 상향**
RunPod `/status`는 GPU 모델을 반환하지 않는다. 워커 핸들러가 `torch.cuda.get_device_name(0)`과 총 VRAM을 output에 실어 보내게 하고, 앱이 이를 컬럼으로 저장한다.

**2.3의 VRAM 오프로딩 가설을 판별하는 유일한 경로이며, 이 판별이 GPU 등급 상향 결정(1.56배냐 2~3배냐)을 좌우한다.** 초판에서는 1-1 다음 순서였으나 상향한다.

**1-3. 완료 무결성 검사**
`poll_runpod_job()`에서 `COMPLETED` 처리 전에 검증한다: 저장된 산출물이 0개이거나 `executionTime`이 하한(예: 5,000ms) 미만이면 COMPLETED로 기록하지 않고 실패로 분류한다. 2.7의 사례를 막는다.

경계: 하한값은 설정 가능한 상수로 두되, 워크플로우별 동적 계산은 하지 않는다(YAGNI).

**1-4. 관리자 화면 지표 분리**
대기(p50/p95)와 실행(p50/p95)을 **분리** 표시한다. 평균이 아니라 백분위를 쓴다 — 표본이 적고 꼬리가 길다. 합산 소요시간만 보면 이번처럼 원인이 보이지 않는다.

**1-5. 정규화 지표**
`executionTime / (frames × 메가픽셀)`을 파생 저장한다. 해상도·길이가 다른 작업 간 비교와 GPU 등급별 대조에 필요하다.

**1-6. 세분화 계측 (Phase 1 확장, 워커 측 선행 필요)**
`delay`/`exec` 2단계로는 "모델 로딩이 느린 건지 GPU가 느린 건지"를 구분할 수 없다. 워커 핸들러가 아래를 분리 보고하면 판별된다:

```
queue → worker boot → model load → ComfyUI execution → VAE decode/encode → output upload
```

특히 **model load**가 분리되면 2.2의 볼륨 병목 가설과 Phase 2의 효과를 직접 측정할 수 있다. 1-2와 같은 워커 수정 작업이므로 함께 진행한다.

**1-7. 동시성 정책 정합성**
`maxActiveTasksTotal`이 엔드포인트 Max Workers를 초과하면 관리자 화면에 경고를 표시한다. 자동 동기화는 하지 않는다 — RunPod 설정은 앱 밖에 있고, 조용히 맞추면 운영자가 불일치를 인지하지 못한다.

### 3.3 Phase 2 — 볼륨 의존 제거

2.2의 스케일아웃 비용과 볼륨 대역폭 포화를 근본적으로 없앤다. **Phase 3의 선행 조건이다.**

선택지는 셋이며 비용·효과가 다르다.

| 방안 | 효과 | 비용 | 샌드박스 환경 공유 |
|---|---|---|---|
| **A. 모델을 워커 이미지에 베이크** | 로컬 NVMe 로딩, 스케일아웃 비용 최소 | 이미지 빌드/롤아웃 파이프라인 필요 | 깨짐 → C의 Workflow Release로 대체 |
| **B. 워커 부팅 시 볼륨 → 로컬 디스크 1회 복사** | 반복 로딩만 개선. 첫 부팅 비용은 남음 | init script만 | 유지 |
| **C. 현행 유지** | — | — | 유지 |

**A가 효과는 가장 크지만 "샌드박스와 볼륨을 공유해 환경을 동기화한다"는 현재 아키텍처 전제를 깨뜨린다.** 그 전제를 대체할 장치가 C 스펙의 **Workflow Release 버전화**(모델 SHA-256 매니페스트 포함)이므로, **A는 C 스펙의 Release 체계와 반드시 묶어서 진행한다.** 단독으로 하면 환경 정합성 보증이 사라진다.

함께 진행할 것: **운영 볼륨과 샌드박스 볼륨 분리, 운영 볼륨은 read-only 원칙.** 현재는 샌드박스에서 모델을 옮기거나 정리하면 운영 중인 서버리스가 실시간으로 깨진다.

B는 A로 가기 전의 저비용 완충으로 검토할 수 있다.

### 3.4 Phase 3 — 세그먼트 병렬화

2.9의 직렬 실행을 없앤다. 세그먼트별로 `/run`을 동시 제출하고 완료 후 백엔드에서 이어붙인다. `output_service`에 segment/final 역할 구분 로직이 이미 있어 이식 부담이 적고, 단일 세그먼트 템플릿(`video_wan2_2_14B_flf2v_2-images-1.json`)도 이미 존재한다.

기대 효과는 세그먼트 수에 반비례한다(6-images 기준 최대 ~1/5).

**순서 제약 — 반드시 Phase 2 이후에 착수한다.**

병렬화는 동시 job 수를 세그먼트 배수로 늘리고, 그만큼 워커가 동시에 스케일아웃하며, 2.2의 볼륨 대역폭 포화를 악화시킨다. 실측이 그 근거다 — `<2분` 간격 제출의 대기 371.6초가 실행 230초보다 크다. **볼륨 의존을 먼저 걷어내지 않고 병렬화하면 실행 시간을 줄인 만큼 대기 시간이 늘어 순효과가 상쇄되거나 역전될 수 있다.**

주의: GPU count per worker 상향은 ComfyUI가 단일 GPU 실행이므로 효과가 없다. "워커 수 × 상위 GPU 1개"가 올바른 방향이다.

### 3.5 Phase 4 — 입출력 전송 구조 (조건부)

2.8의 페이로드 한계를 해소한다. 입력은 S3 presigned URL을 워커가 내려받고, 출력은 워커가 S3에 올린 뒤 URL만 반환한다. `save_runpod_outputs()`가 이미 `type: "s3_url"`을 처리하므로 백엔드 수신부 수정은 작다.

**전제 확인**: 현재 `STORAGE_BACKEND`는 `local`(EFS)이다. S3 백엔드는 코드 경로만 있고 운영에서 쓰이지 않는다. 따라서 이 단계는 "기존 S3 인프라 활용"이 아니라 **신규 구축**이며 비용을 그렇게 잡아야 한다.

**착수 조건**: 2.8에 정리한 대로 현재 사용 범위(입력 1장, 최악 5.3MB)에서는 한도까지 여유가 크다. **지금 착수하지 않는다.** Phase 3로 입력 이미지 수가 늘거나, 해상도를 올리거나, 다중 입력 템플릿을 운영에 투입하는 시점에 필수가 된다.

출력 측은 별개 판단이 가능하다 — 생성 시간 자체보다 **완료 후 저장·표시 지연**을 줄이는 효과가 있으므로, 영상 길이를 늘리는 결정이 나오면 입력보다 먼저 검토할 수 있다.

## 4. 구현 순서

```
Phase 0 (콘솔)  ── Job TTL, Max Workers, Idle Timeout, GPU 풀
   │              └ Execution Timeout은 조치 완료
Phase 1 (계측)  ── 1-1 컬럼 승격 → 1-2 GPU 확보 + 1-6 세분화(워커 수정 동시)
   │              → 1-3 무결성 → 1-4/1-5 노출 → 1-7 정합성
   │
   ├─ 여기서 재측정. VRAM 가설 판별, Max Workers 상향 효과 확인
   │
Phase 2 (볼륨)  ── C 스펙의 Workflow Release와 묶어서 진행
   │
Phase 3 (병렬화) ── Phase 2 완료 후에만 착수
   │
Phase 4 (S3 I/O) ── 조건부. 입력 이미지 수·해상도가 늘 때만 착수
```

Phase 3(병렬화)은 세그먼트가 여러 개인 템플릿에서만 효과가 있다. **현재 운영은 입력 1장·단일 세그먼트 템플릿이 대부분(61/109건)이므로 Phase 3의 실효 범위도 그만큼 제한된다.** 다중 세그먼트 워크플로를 다시 쓸 계획이 확정될 때 착수 여부를 재판단한다.

## 5. 검증 기준

Phase 0 적용 후 최소 2주, 또는 신규 작업 30건 이상 축적 시점에 2.1과 동일한 방식으로 재측정한다.

| 지표 | 현재 | 목표 | 확인 단계 |
|---|---|---|---|
| delay p90 | 496.8s | < 120s | Phase 0 후 |
| delay p95 | 682.7s | < 300s | Phase 0 후 |
| TIMED_OUT 비율 | 16.5% | < 3% | Phase 0 후 |
| exec p95 / timeout | 86.2% → 43.1% | < 50% | 조치 완료 |
| exec 워커별 정규화 편차 | 1.56배 | < 1.2배 | Phase 1 후 |
| model load 시간 | 측정 불가 | Phase 2 전후 비교 | Phase 1-6 후 |
| 다중 세그먼트 생성 시간 | 세그먼트 수 비례 | ~1/N | Phase 3 후 (조건부) |

Phase 1-1 완료 후에는 이 재측정이 관리자 화면에서 바로 가능해야 한다 — 운영 컨테이너 진입이 다시 필요하다면 1-1이 실패한 것이다.

## 6. 테스트

- **1-1**: 마이그레이션 up/down. `poll_runpod_job()`이 세 컬럼을 채우는지, `runpod_status_json`에 필드가 없을 때 NULL로 남는지.
- **1-2/1-6**: 워커가 GPU 정보·단계별 시간을 보내지 않는 구버전 응답에서도 예외 없이 NULL 처리되는지(하위 호환).
- **1-3**: 산출물 0개 + 짧은 `executionTime`인 RunPod 응답이 COMPLETED가 아닌 실패로 분류되는지. 정상 응답 회귀 없음.
- **1-4/1-5**: 백분위·정규화 계산이 표본 0건·1건에서 예외를 내지 않는지.
- **1-7**: 정책값이 Max Workers 이하/초과일 때 경고 표시 여부.
- **Phase 3**: 세그먼트별 job 실패 시 부분 실패 처리, 이어붙이기 순서 보장.
