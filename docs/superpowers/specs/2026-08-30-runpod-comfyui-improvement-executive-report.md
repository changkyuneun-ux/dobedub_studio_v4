## 1. 보고 목적 및 실행 요약

현재 운영 중인 ComfyUI i2v(Image-to-Video) 서버리스 파이프라인의 **심각한 지연 시간(성능)**과 **결과물 왜곡·모션 저하(품질)** 문제를 추정이 아닌 **실운영 데이터(109건 전수 분석)**를 통해 규명했습니다.

1. **성능 원인 규명**: 
   - 사용자가 체감하는 지연의 절반 이상은 GPU 연산이 아닌 **큐 대기 및 스케일아웃 대기(p90 기준 대기 497초 > 실행 470초)**였습니다.
   - 1일 이상 유휴 상태였던 엔드포인트도 10초 만에 기동하므로 유휴 콜드스타트는 정상이지만, **요청이 몰릴 때 신규 워커가 네트워크 볼륨(NFS)에서 30GB+ 모델 세트를 중복 로딩하면서 I/O 포화 및 큐 만료(실패율 16.5%)**가 발생했습니다.
2. **품질 원인 규명**: 
   - 사용자의 97%는 기본값을 그대로 사용하고 있으나, **템플릿과 설정의 기본값·상한선 자체가 모델의 권장 범위를 벗어나도록 구성**되어 있었습니다.
   - 모델 학습 윈도우(81프레임/5초)를 초과하는 **161프레임(10초) 요청이 전체의 26%**에 달해 후반부 왜곡을 유발했고, 4-step 증류 LoRA에 고CFG(1.8~3.9) 노출, 비표준 해상도 사용 등이 품질 저하를 가중했습니다.
3. **3일 실행 범위**:
   - RunPod 콘솔의 작업 TTL, worker capacity, idle 설정을 애플리케이션 동시 작업 정책과 정합시킨다.
   - 서버측 파라미터 검증, 완료 무결성 검사, 실행시간 계측을 구현한다.
   - 프레임·FPS·CFG·motion shift 등 확인된 템플릿 결함을 교정하고, 골든 테스트로 실제 결과를 검증한다.
4. **후속 구조 개선**:
   - 3일 조치에서 수집한 GPU·모델 로딩 데이터를 근거로 운영 Serverless 전용 이미지, 운영/샌드박스 Volume 분리, Workflow Release 체계를 다음 단계에서 구현한다.

* **대기 시간 급증**: 대기 시간이 p50(14초)에서 p75(356초)로 **25배 급증**합니다.

  - 직전 작업 후 `< 2분` 내 인입: 대기 중앙값 **371.6초** (스케일아웃 병목)

### 3.1 성능 저하 원인
1. **네트워크 볼륨(NFS) 스케일아웃 I/O 병목**:
   - 여러 사용자가 동시에 요청하거나 연속 생성 시, 추가 기동되는 워커들이 공유 Network Volume에서 Wan 2.2 14B(High/Low Noise FP8 2개 + LoRA + VAE + Text Encoder = 30GB+)를 동시에 읽어 대역폭이 고갈됩니다.
2. **엔드포인트 설정과 애플리케이션 정책 불일치**:
   - 백엔드는 최대 10개 동시 작업을 수락(`maxActiveTasksTotal = 10`)하지만, RunPod 엔드포인트 `Max Workers`는 7개로 제한되어 있어 3개 작업은 큐에서 무기한 대기하다 만료되었습니다.
3. **24GB GPU에서의 VRAM 오프로딩 의심**:
   - Wan 14B 모델 세트는 약 22~28GB의 VRAM을 요구합니다. 24GB GPU 환경에서 실행될 경우 시스템 RAM과 VRAM 간 스와핑(오프로딩)이 발생하여 단일 워커 내에서도 속도 편차가 최대 3.1배까지 벌어졌습니다.

### 3.2 품질 저하 원인
1. **학습 윈도우 초과 (161프레임 요청 26%)**:
   - Wan 2.1 모델의 최적 학습 윈도우는 81프레임(5초)입니다. UI 상한선이 10초(`161프레임`)로 열려 있어 사용자가 이를 선택할 경우 후반부 모션 뭉개짐과 배경 드리프트가 필연적으로 발생했습니다.
2. **비표준 해상도 사용으로 인한 모션 왜곡**:
   - DiT(Diffusion Transformer) 아키텍처 특성상 패치 단위(16/32 배수)의 네이티브 해상도(832×480, 1280×720 등)를 벗어난 720×720, 688×784 등 임의 해상도 사용 시 형태 왜곡이 심화되었습니다.
3. **위험한 파라미터 노출 및 서버 검증 부재**:
   - 4-step 스텝 증류 LoRA 환경에서는 `CFG=1.0`이 필수임에도 UI 노브가 12.0까지 열려 있어 `CFG=1.8~3.9`로 설정된 작업에서 채도 왜곡 및 노이즈가 발생했습니다.
   - `motionShift` 최소값이 2.0으로 선언되었으나 서버 검증이 없어 1.0으로 통과된 사례가 존재했습니다.
4. **템플릿 인코딩 결함**:
   - `3~6-images` 템플릿의 경우 세그먼트는 16fps로 생성하고 최종 영상은 24fps로 인코딩되어 영상이 1.5배 빠르게 재생되는 결함이 확인되었습니다.

### 3.3 아키텍처 및 거버넌스 원인
1. **샌드박스(개발)와 서버리스(운영) 환경 미분리**:
   - 동일한 볼륨을 공유하므로 샌드박스에서 커스텀 노드나 모델을 수정·삭제할 경우 운영 서버리스가 즉시 다운될 위험에 노출되어 있습니다.
2. **미등록 템플릿 자동 활성화 및 결함 복제**:
   - 운영 중인 13개 워크플로우 중 7개가 검증 이력이 없으며, 자동 생성기가 결함 있는 스위치 분기 설정을 새 템플릿에 그대로 복제하고 있었습니다.

## 4. 종합 해결 방안

### ① 인프라 및 RunPod 엔드포인트 설정
* **Job TTL 상향**: 큐 대기 시간과 실행 시간을 포괄하도록 TTL을 상향하여 큐 대기 중 억울하게 만료되는 16.5%의 실패 방지.
* **Max Workers 조정 (7 ➔ 10)**: 애플리케이션 정책과 일치시켜 큐 대기 지연을 해소한다. WAN i2v는 GPU Worker당 동시 실행을 1로 유지하고, 처리량은 Worker 수로 확장한다.
* **Idle Timeout 상향 (60s ➔ 300s)**: 직전 작업과의 간격이 짧을 때 워커가 살아있도록 하여 30GB 모델 재로딩 방지.
* **Execution Timeout 조정 완료**: 600s ➔ 1200s (기완료 조치로 실행 타임아웃 여유 45% 확보).

### ② 서버 및 파라미터 거버넌스 (품질 즉시 정상화)
* **서버측 파라미터 범위 강제 (Fail-Closed)**: 브라우저 UI뿐 아니라 백엔드 API 진입점(`job_service.py` / `workflow_patch_service.py`)에서 `CFG`, `Steps`, `Shift`의 min/max를 엄격히 강제.
* **4-Step LoRA 모드 CFG=1.0 강제 잠금**: 왜곡 발생 원천 차단.
* **Shift 하한 5.0 상향 및 네이티브 해상도 프리셋 제공**: 일관된 화질 보장.
* **템플릿 FPS 일치화**: 세그먼트 생성 FPS와 CreateVideo 인코딩 FPS를 16fps로 단일화.

### ③ 계측 및 모니터링 체계 구축
* **타이밍 지표 컬럼 승격**: `workflow_tasks` 테이블에 `runpod_delay_ms`, `runpod_execution_ms`, `runpod_worker_id` 컬럼 추가.
* **GPU 모델 정보 수집**: 워커 핸들러 응답에 GPU 모델(`torch.cuda.get_device_name`)을 포함하여 VRAM 오프로딩 여부를 확정 진단.
* **완료 무결성 검사**: 실행시간이 비정상적으로 짧거나(예: < 5초) 출력물이 0개인 비정상 작업을 자동으로 실패(FAILED) 처리.

### ④ 2단계 비디오 생성 파이프라인 (중장기 품질·속도 혁신)
* **Fast DiT + RIFE 보간 구조**:
  - 확산 모델에서 161프레임을 직접 생성하지 않고, **81프레임(5초, 16fps)을 고품질로 생성한 후 RIFE 프레임 보간 노드로 30fps/60fps 확장**.
  - 생성 시간 50% 단축 및 모션 부드러움 극대화.

### 5.1 일일 공통 운영 방식

- 각 일자 종료 시 코드 변경, RunPod 콘솔 변경, DB migration 적용 여부를 하나의 실행 로그에 기록한다.
- Day 1~2 변경은 staging 또는 제한된 테스트 workflow에서 먼저 검증한 후 운영 workflow에 반영한다.
- 실운영 작업 데이터는 수정하거나 삭제하지 않는다. 신규 계측 컬럼은 기존 행을 비워 두고 이후 작업부터 채운다.

## 7. 3일 완료 후 연계 작업

3일 조치는 현행 Serverless 구조에서 즉시 적용 가능한 안정화 작업이다. 아래 항목은 Day 3의 계측 결과와 골든 테스트를 입력으로 이어서 진행한다.

1. **GPU 및 worker tier 재조정**: GPU 모델·VRAM·정규화 실행시간을 근거로 24GB급 GPU 유지 또는 48GB급 GPU 전환을 판단한다.
2. **운영 환경 분리**: Sandbox 개발 Volume과 Serverless 운영 Volume을 분리하고 운영 Volume은 read-only로 관리한다.
3. **Workflow Release 도입**: workflow JSON, paramconfig, custom node version, 모델 SHA-256, 대표 입력·seed·기대 출력값을 하나의 검증 가능한 release로 관리한다.
4. **모델 로딩 구조 개선**: 자주 쓰는 모델의 cached model 또는 worker image bake, 필요 시 Volume→로컬 디스크 초기 복사 방식을 비교한다.
5. **다중 세그먼트 병렬화**: Volume 병목 제거와 release 검증 체계가 마련된 이후에만 세그먼트별 작업 분리를 검토한다.
