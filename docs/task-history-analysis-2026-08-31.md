# 작업 이력 분석 — 사용자 · 일자 · 워크플로우

- 작성일: 2026-08-31
- 데이터: 운영 RDS `workflow_tasks` 전량 111건 (삭제 2건 제외 **109건**), 2026-08-06 ~ 2026-08-21
- 조회 방법: ECS Exec으로 운영 컨테이너에 진입해 읽기 전용 `SELECT`
- 관련 문서: [A 성능 설계](superpowers/specs/2026-08-30-runpod-performance-design.md) · [진단 보고](runpod-i2v-improvement-report-2026-08-30.md)

> **해석 시 주의**: 이 문서는 개인의 성과를 평가하지 않는다. 사용자별로 나눈 이유는 **시스템이 어떤 사용 방식에서 무너지는지**를 보기 위해서다. 실제로 확인된 것은 특정 개인의 문제가 아니라, 시스템이 정보를 주지 않을 때 사람이 자연스럽게 하게 되는 행동이 실패로 이어진다는 구조다.

## 2. 가장 중요한 발견 — 실패는 특정 조건에서만 발생했다

### 2.1 동시 제출 제한 정책 도입 전후

앱의 동시 활성 Task 제한(사용자당 3건 / 전체 10건)이 **2026-08-12**에 설정됐다.

| 구간 | 건수 | TIMED_OUT | 기타 실패 | 대기 중앙값 | 2분내 연속제출 |
|---|---|---|---|---|---|
| **도입 전** (08-06 ~ 08-11) | 84 | **18건 (21.4%)** | 2건 | 58.1초 | 24회 |
| **도입 후** (08-13 ~ 08-21) | 25 | **0건 (0%)** | 2건 | **11.4초** | 4회 |

**큐 만료가 정책 도입 후 한 건도 없다.** 대기 시간 중앙값도 5배 개선됐다.

도입 후 남은 실패 2건은 성격이 다르다 — 하나는 사용자 취소(08-13), 다른 하나는 192프레임 요청으로 인한 실행 오류(08-20)다. **줄서기 문제가 아니다.**

### 2.2 이 결과를 확정할 수 없는 이유

같은 시기에 **사용 패턴도 함께 바뀌었다.** 2분 내 연속 제출이 24회에서 4회로 줄었다. 정책이 막은 것인지 사용자가 스스로 간격을 두게 된 것인지 데이터로는 분리되지 않는다.

또한 도입 후 표본은 **25건 / 9일**이다. 도입 전(84건 / 6일)의 3분의 1에 못 미친다.

**따라서 이 데이터가 말할 수 있는 것은 "재발 조건이 사라졌을 수 있다"까지다.** 정책을 되돌려 인과를 확인하는 실험은 권하지 않는다 — 잃을 것이 얻을 것보다 크다.

### 3.1 연속 제출 비율과 실패율이 정비례한다

```
함승현   연속제출 43.1%  →  실패율 28.8%
박진우   연속제출  3.4%  →  실패율  6.7%
송승화   연속제출  0.0%  →  실패율  0.0%
```

세 사람에서 순서가 정확히 일치한다. **실패는 사용량이 아니라 제출 간격을 따라간다.**

### 3.2 예외 두 건은 표본이 설명한다

**플랫폼(33.3%)** — 연속 제출이 0%인데 실패율이 높다. 그러나 6건 중 2건이고, 그중 하나는 `steps=15`로 인한 실행 오류다(줄서기와 무관). 통계적 의미를 두기 어렵다.

**송승화(대기 498.8초, 실패 0%)** — 대기가 가장 길지만 실패가 없다. 6건을 이틀에 나눠 띄엄띄엄 썼기 때문에 매번 워커를 새로 띄우는 비용을 온전히 냈지만, 뒤에 줄이 없어 만료되지 않았다. **대기가 길다고 실패하는 것이 아니라, 줄이 길 때 실패한다는 점을 보여주는 대조군이다.**

### 4.1 08-10 하루가 전체 실패의 68%를 만들었다

비완료 22건 중 15건, 시스템 실패 20건 중 15건(75%)이 이날에 있다. 그날의 시간 흐름을 복원하면 원인이 드러난다.

```
06:10 ~ 06:31   14건 연속 제출 (간격 1~318초)   전부 COMPLETED
                └ 대기 시간이 점점 늘어남: 138 → 353 → 431 → 472 → 442 → 404 → 372초

07:25           TIMED_OUT                      ← 첫 실패
08:40           COMPLETED (대기 1,622초 = 27분)  ← 재시도, 겨우 성공

10:48:49 ~ 10:49:12   13건을 23초 만에 일괄 제출   ← 전부 TIMED_OUT
11:03                 1건 추가 제출              ← 역시 TIMED_OUT
```

06시대에 이미 대기가 400초대로 쌓이고 있었고, 07:25에 첫 만료가 났으며, 재시도가 27분 걸렸다. 그리고 10:48에 13건이 한꺼번에 들어갔다.

**느리니까 몰아넣고, 몰아넣으니까 더 실패하는 악순환이 그대로 기록되어 있다.**

핵심은 이것이 무리한 사용이 아니었다는 점이다. 화면에는 **얼마나 밀려 있는지, 얼마나 기다려야 하는지 표시되지 않는다.** 정보가 없으면 "여러 개 넣어두고 기다리자"가 합리적인 선택이 된다.

### 4.2 작업 시간대가 중간에 완전히 바뀌었다

| 구간 | 건수 | 09시 이전 비율 |
|---|---|---|
| 08-06 ~ 08-13 | 95 | **85.3%** (81건) |
| 08-18 ~ 08-21 | 14 | **0%** |

초기에는 심야에 몰아서 작업했고, 08-18 이후로는 전부 업무시간이다. **2절의 정책 효과가 이 패턴 변화와 겹쳐 있어 인과가 분리되지 않는 직접적 원인이다.**

전환 사유는 확인되지 않았다. 초기 온보딩·테스트 집중 사용이 끝난 것인지 운영 방침이 바뀐 것인지에 따라 향후 부하 예측이 달라진다.

### 4.3 사용 밀도

09일간 109건이며 하루 평균 12건이지만, 실제로는 **08-10 하루가 37건으로 전체의 34%**다. 08-18 이후 4일은 합쳐서 14건이다. 부하가 균등하지 않다.

## 6. 종합

1. **실패는 시스템 용량이 아니라 제출 방식과 상관한다.** 사용자별 연속 제출 비율과 실패율이 정비례하고, 실패의 68%가 하루에, 그중 대부분이 23초 사이 일괄 제출에서 나왔다.

2. **그 하루의 행동은 시스템이 유발했다.** 대기가 400초대로 쌓이고 재시도가 27분 걸리는데 화면에는 아무 정보가 없었다. 정보 없이 기다리면 몰아넣는 것이 합리적 선택이 된다.

3. **동시 제출 제한 정책 이후 큐 만료가 멈췄다.** 다만 사용 패턴 변화와 겹쳐 인과가 분리되지 않고 표본이 25건이라 확정할 수 없다.

4. **워크플로우별 지표는 사용자 편향을 크게 받는다.** `Pickme_v3`의 42.3%는 워크플로우가 아니라 특정 하루의 산물이다.

5. **실행 시간은 프레임 수로 설명된다.** 워크플로우 간 효율 차이는 보이지 않는다.

## 7. 설계 반영

이 분석으로 [A 성능 설계](superpowers/specs/2026-08-30-runpod-performance-design.md)를 두 곳 수정했다.

**긴급도 조정** — Job TTL과 Max Workers 상향을 *현재 장애의 해결책*에서 *재발 방어책*으로 재분류했다. 큐 만료가 이미 0건이기 때문이다. 다만 원인이 미확정이고 비용이 0이므로 폐기하지는 않는다. 지금 체감 성능을 움직이는 것은 Idle Timeout과 GPU 풀이다.

**신규 항목 (Phase 1-8) — 사용 방식 완화**

- 큐 상태를 제출 화면에 노출한다 (대기 건수, 예상 대기 시간)
- 연속 제출 시 안내한다. **차단하지 않는다**
- 실패 작업의 재시도 동선을 만든다 — 수동 재제출 반복이 일괄 제출로 이어진다

원인이 사용 방식이라면 대응도 UI에서 가능하며, 인프라 변경보다 훨씬 저렴하다. **이번 분석에서 나온 가장 비용 효율이 높은 대응이다.**

| 항목 | 내용 |
